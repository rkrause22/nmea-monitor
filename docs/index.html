NMEA-0183 Weather Data over LoRa

Russel Krause and Peter van Muyden

Problem Statement

Our sailing club wanted to replace an aging anemometer on our race committee (RC) boat and researched a few options before settling on the AirMar 200WX.  Our race officer had experience with the AirMar and felt it most adaptable for our situation, knowing that it was capable of producing data that could be displayed and consumed aboard the RC boat and hoping it could be transmitted to shore (1-3 kms away) over a line-of-sight LoRa link where the data could also be displayed and stored. A NMEA 0183 capable device was chosen because of its compatibility for serial transmission over the LoRa link.

There may be more inexpensive solutions for this problem, but we wanted a system that was well trusted in the industry and that was adaptable for both onboard and onshore data analysis.

Overview

The system collects and displays NMEA-0183 weather/navigation data from an AirMar anemometer mounted on our sailing club’s race committee boat, displays it on a Garmin display, then transmits it over a WaveShare LoRa serial link, and receives it at a shore station where a Raspberry Pi runs Python scripts to filter, aggregate, store, and display the data as HTML, accessible on a display in the clubhouse as well as from our club website.

Onboard Device Connections

The Airmar 200WX supports both NMEA 0183 and NMEA 2000 and uses separate cables for each interface. Since we were going to be transmitting data serially (not packed-based), we chose to use the NMEA 0183 interface cable. Conveniently, our purchase came with both cables, we just left the NMEA 2000 cable in the box.

Through experimentation, we learned that the NMEA 0183 interface is most compatible with RS422 serial adapters after first implementing an RS232 serial adapter.  With RS232, we found that we were able to transmit the AirMar data stream easily enough, but were not able to send configuration data back to the AirMar over RS232, making it necessary to temporarily connect an RS422 adapter to configure the AirMar.  In the end, we decided to use RS422 exclusively on the boat side as it simplified the wiring and allowed us the ability to configure the AirMar directly with the RS422/USB adapter.

Onshore Device Connections

Thankfully, the connections between the shore-side LoRa and the Raspberry Pi are much simpler!  Here we just used an off-the-shelf RS232-USB cable and it worked in both directions.  We actually tried using the RS422 connection on the shore side and it did not work as well.

Device Configuration

The sections below describe the configurations each of the onboard devices require.

AirMar 200WX Configuration

To avoid saturating the LoRa at 4800 baud, the AirMar needed to be configured to reduce its output to only the necessary messages and only then at a low repetition rate.  These changes were made using a terminal program by issuing the following commands as described in the AirMar WeatherStation Technical Manual ( https://www.psicompany.com/man-prod-info/furuno/prodweb/nav/pb100tech.pdf ) using the RS422 to USB adapter that we wired in onboard (or by sending them back from shore using the shore-side USB adapter).

  • $PAMTC,BAUD,4800                // set the baud rate to 4800
  • $PAMTX,0                        // temporarily stop NMEA transmissions
  • $PAMTC,EN,ALL,0                // disable all sentence transmissions
  • $PAMTC,EN,ZDA,1,13        // enable ZDA (time message) every 1.3 seconds
  • $PAMTC,EN,MWD,1,17        // enable MWD (weather message) every 1.7 seconds
  • $PAMTC,EN,MDA,1,29        // enable MDA (weather message) every 2.9 seconds
  • $PAMTC,EN,GGA,1,37        // enable GGA (GPS message) every 3.7 seconds
  • $PAMTC,EN,S                // save settings to CMOS
  • $PAMTC,EN,Q                // echo settings for confirmation
  • $PAMTX,1                        // restart NMEA transmissions

After making these setting changes, we power cycled the AirMar and then echoed the settings back using $PAMTC,EN,Q to make sure they were saved correctly.

You might notice the odd distribution of message timings.  We chose period lengths as prime numbers between command outputs to ensure message collisions would redistribute over time.  These numbers work, but there are still collisions in the LoRa transmissions at 4800 baud and these rates may need more refinement.  The Python listener had to be written robustly to deal with over-written messages, and uses message averaging over multiple ZDA time “frames” to manage the data mangling.

LoRa Configuration

Each LoRa has to be configured before use to ensure they are “paired” for communication, and so that their transmission settings match the AirMar. See the SX1262-LoRa-DTU-xF manual ( https://www.waveshare.com/wiki/SX1262-LoRa-DTU-xF?srsltid=AfmBOoprBd069ecNsMlJdKJpC65VUkA-s1yuACzGc4LBFTF1aM_M_bUH ) for more information.

By default, the LoRa is configured to use RS232 at 9600 baud.  To switch between RS232 and RS422, you press the “Key” button once ( see caution below ) using an initial connection of 9600 (which you need to change to 4800 as below).

The device uses “modem-like” (AT) commands to update its settings issued via the RS422 to USB connector, but before you issue any AT commands, you need to temporarily disable the AirMar transmissions.

  • $PAMTX,0                        // temporarily stop AirMar NMEA transmissions
  • +++                                // type three “+” quickly and wait
  • AT<cr><lf>                        // should echo OK
  • AT+BAUD=4800                // 4800=Baud rate (default is 9600)
  • AT+BAUD?                        // should echo 4800
  • AT+BW=1                        // 1=250Khz (default 0=125Khz)
  • AT+BW?                        // should echo 1
  • AT+MODE=1                        // 1=Streaming mode
  • AT+MODE?                        // should echo 1
  • AT+PORT=1                        // 1=RS422 mode (onboard); 3=RS232 mode (onshore)
  • AT+PORT?                        // should echo 1 (afloat), 3 (ashore)
  • AT+EXIT                        // Saves settings and restarts device
  • $PAMTX,1                        // restart AirMar NMEA transmissions

Perhaps the key configuration here is the transmission bandwidth at 250Khz (AT+BW=1). Some research indicated that transmitting at the default 125Khz would exacerbate the buffer overruns since the time it takes to transmit the data over air at 125Khz might be longer than it takes to fill the buffer at 4800 baud.  The tradeoff is that the higher frequency diminishes the transmission distance, however we hope that 250Khz will perform well enough over 1-3km.

NOTE: Afloat, we use the LoRa’s RS422 configuration because it is much better matched to the AirMar interface.  Ashore, we were able to use the simpler RS232 connection between the LoRa and the Raspberry Pi. So long as the BAUD and MODE are the same between the LoRas, they can communicate with each other.

CAUTION : Be very careful not to press the key button within 3 seconds of powering the device on  - doing so will put the device into upgrade mode, and this cannot be reset without uploading a new bios update… This happened to us and we had to complete a BIOS upgrade to unbrick the device!  See manual for more details.

Garmin Configuration

Because we disabled many of the AirMar’s NMEA output sentence types, very few (if any) of the default screens will show any data.  We simply deleted all the default screen configurations and created a new screen that only showed Wind Speed and Wind Direction (since that is all we need on our RC boat).

Software

The raw NMEA 0183 sentences are received by a Raspberry Pi after being transmitted over the LoRa. As mentioned above, these messages are sometimes garbled and/or over-written.  Fortunately, we are able to use the NMEA sentence checksums to validate which messages are acceptable.

We created two Python scripts:

  • nmea_filter.py  to read, filter and forward averaged NMEA data to the repository; and
  • nmea_repository.py  to store and serve the data via a repository.

nmea_filter.py

  • Listens to the ttyUSB0 serial port for incoming sentences (each terminated with \r\n).
  • Validates each sentence using their checksums
  • Filters out unwanted sentence types (we only use ZDA, WMD, MDA and GGA types)
  • Aggregates all WMD, MDA and GGA sentences received over a configurable number of ZDA time frames
  • Sends each ZDA frame aggregation of WMD, MDA, GGA sentences to the repository

One record is sent to the repository for each set of ZDA frame aggregations received.  Within the period between ZDA sentences, zero or more WMD, MDA, GGA sentences may be received.  Each of these sentence types is aggregated into one sentence of each type, so that, at most, each ZDA frame will contain 1 WMD, 1 MDA and 1 GGA sentence. The aggregation method depends on the type of data, but generally: wind direction, wind strength, temperature, barometric pressure, latitude, longitude, etc are averaged, other data such as time, may be selected as the first or last of the data received.

nmea_repository.py

The repository is a REST service that provides the following methods (among others):

  • add: accepts a ZDA frame aggregation from nmea_filter.py and appends it to a text file as JSON object.
  • last: returns the latest (n) ZDA frame aggregation(s) as NMEA 0183 sentences
  • weather: returns an aggregation of weather data for a given time span
  • history: returns wind direction and strength data to plot a graph for a given time span

Like nmea_filter.py, the repository also aggregates data over (longer) time periods. In our HTML presentation by default, we show an aggregation of data over the past 30 minutes, but the user can select any period from our database.  (data over 1 year-old is purged).

Improvements

The failure rate we see on the LoRa connection remains quite high. However, by confirming the checksums on each NMEA sentence, we have confidence which sentences are valid and which are not and we were able to simply ignore those that are corrupt or incomplete, but this is not ideal.

The LoRa device we have chosen does have a “packet mode” which can send up to 960 bytes in a single message, which would be more than enough for each NMEA sentence, however, the device requires that each packet is prepended with 3 bytes to identify the packet. Since we do not have any device onboard capable of modifying the sentences before sending them, we cannot use this feature.

If we were to add a device onboard (such as a Raspberry Pi or Arduino), we could potentially filter and aggregate the NMEA messages before sending them over the LoRa, further reducing the bandwidth requirements and then use packet mode to send them - something we may consider in the future.
